支付模块（含回调）

P0真实支付下单失败被静默回退成"模拟支付并立即发货"server/routes/user.js · /orders/:id/pay

现象：wx/alipay/虎皮椒真实下单抛出异常后，代码 catch 后继续走到"模拟支付"分支，直接调用 settlePaidOrder 把订单置为已支付并发卡。

根因/影响：攻击者可故意制造真实下单失败（超时、参数篡改、并发），免费拿到卡密；这是最直接的"白嫖"通道。

修复：下单失败必须返回错误提示，禁止回退模拟支付；模拟支付仅允许在 settings.paySandbox === true 时使用，且要在代码里显式断言。

P0线上配置仍开启沙箱模式，全站支付不真实扣款data/db.json · server/payments.js

现象：当前 db.json 中 paySandbox: true；且 payments.configured() 在沙箱开启时直接返回 false，即使填了真实商户密钥也不生效。

根因/影响：所有订单都会落入模拟支付，买家不付款也能拿货。若以当前配置直接上线，等于免费发放。

修复：上线前必须关闭沙箱并完整配置微信/支付宝/虎皮椒密钥；configured() 逻辑改为"沙箱模式仅开发环境生效"，生产环境由密钥完整性决定。

P0支付回调无幂等保护，结算失败时置"refunded"却无真实退款server/routes/pay.js · /notify/wechat /notify/alipay

现象：① 微信/支付宝回调入口未先查订单状态，重复通知会重复进入结算流程（靠 settle 内部 status 校验兜底，但回调应直接幂等返回）；② settlePaidOrder 失败时把订单置为 refunded 并发站内消息"已拦截并发起退款"，但代码里没有调用任何真实退款接口。

根因/影响：用户已付款却拿不到货时，系统假装"已退款"，实际钱没退，引发资损与客诉；微信侧订单不存在还返回 404 JSON，不符合微信要求的 SUCCESS/FAIL 约定，会持续重试。

修复：回调入口统一幂等（订单非 pending 直接返回 SUCCESS）；结算失败改为告警 + 人工介入 + 调用退款 API；微信回调始终按协议返回。

P2微信平台证书解密为死代码，未配置证书直接拒回调server/payments.js

现象：wxDecryptResource 中 Buffer.from(resource.associated_data ? '' : '', 'utf8') 恒为空串，解密逻辑不成立；未填平台证书时回调直接拒绝，且没有自动下载微信平台证书的能力。

修复：按 APIv3 规范实现 AEAD_AES_256_GCM 解密（ciphertext 包含 nonce 前 12 字节），或接入证书自动下载；系统设置中提供平台证书下载引导。

分站上下级模块（重点）

P1购物车混入两个分站商品时，订单只归属第一个分站server/routes/user.js · POST /orders（branchId 取值）

现象：订单 branchId 用 calc.goods.find(g => g.branchId).branchId 只取第一个分站商品；但分成（settle.creditBranchShare）按每个商品的 branchId 分别入账。

根因/影响：第二个分站的钱照拿，但在分站后台按 order.branchId === 自己 查不到该订单，无法发货、无法核销——分成与订单可见性脱节。

修复：方案 A：下单时按分站拆成多条订单（每个分站一条）；方案 B：订单记录 branchIds[]，分站订单查询按"订单内包含本分站商品"过滤，发货只允许操作本分站的 goods 行。

P1一级分站价格没有平台价下限，可把下级价格设成 0server/routes/branch.js · PUT /price；server/branch-sign.js · validatePriceBelow

现象：validatePriceBelow 只做"当前价格 ≥ 上级价格"的上溯校验；一级分站 parentId = 0（上级是平台）时，没有与 settings.branchProPrice / branchNormalPrice（平台统一开通价）比较。

根因/影响：一级专业分站可把专业/普通开通价设为 0，整条链路的下级开通费变成 0，平台与各级分站的收益结构被击穿。

修复：parent 为空时下限取平台设置价：pricePro ≥ settings.branchProPrice、priceNormal ≥ settings.branchNormalPrice。

P1总站删除源商品后，分站商品价格下限失效（可无限降价）server/routes/branch.js · PUT /branch/products/:id / POST /branch/products

现象：分站改价时用 d.products.find(src) 实时找总站源商品；源商品被删除后 src 为空，min 退回商品自身价格，约束形同虚设。

根因/影响：分站可在源商品下架/删除后任意降价，把下游价格打穿；同时上架新商品时也无法再校验旧下限。

修复：上架/改价时把 floorPrice（上级同款价或总站价）快照固化到分站商品记录，改价只与快照比较，不依赖实时查源；源商品变动时提供"重新同步"刷新快照。

P1分站密码单向同步：分站改密不回写用户账号server/routes/branch.js · PUT /password；server/routes/auth.js · syncBranchPassword

现象：用户在前台改密码会同步到名下分站（syncBranchPassword）；但分站在后台改密码注释明确"不回写用户账号"。

根因/影响：同一账号（邮箱）既是用户又是分站，两边密码可不同步。用户以为"同一个账号同一密码"，改完分站密码后前台登录仍是旧密码，容易困惑；反之用户改密码后分站密码被强制改掉，代理可能不知情。

修复：双向同步：分站改密时若 ownerId > 0 回写对应用户密码（并清理其会话）；或明确提示"两处密码独立"并在 UI 上区分。

P2邀请链接协议取 req.protocol，反代后可能生成 http 链接；签名默认永久有效server/routes/branch.js · GET /invite-link

现象：拼接链接用 req.protocol，未配置 trust proxy 时经 Nginx 反代会得到 http://；signInvite 未显式传过期时间（exp=0 表示永久）。

修复：启用 app.set('trust proxy', 1) 并优先取 x-forwarded-proto；邀请签名显式设置有效期（如 30 天）并在页面文案一致。

P2数据库残留测试分站：ownerId=0 的一级分站"112"data/db.json · branches[0]（id=2, parentId=0, ownerId=0）

现象：当前库里有一个 name=112, type=pro, parentId=0, ownerId=0 的分站。它没有绑定用户，按现有规则无法升级、无法用账号登录，是上一轮报告中"管理员建站体系断裂"的活样本。

修复：在管理端分站列表删除该测试分站，或补绑一个真实用户（ownerEmail）使其可登录、可升级。

用户与认证模块

P1用户余额扣款不写资金流水（开通/加入/升级分站）server/routes/user.js · open-branch / join-branch；server/routes/branch.js · upgrade

现象：用户余额在开通分站、加入下级分站、补差价升级时被扣减，但三处都不写 balanceLogs（只有分站侧有 branchBalanceLogs）。

根因/影响：用户端无法核对余额去向，管理端对账缺少用户余额流水，扣错/重复扣款难以追溯。

修复：统一新增用户余额流水表（类型：branch_open / branch_join / branch_upgrade / admin_adjust / refund），与分站流水对称；管理端余额调整也补记。

P1个人资料可直接修改邮箱且无查重 → 账号混淆/被盗风险server/routes/auth.js · PUT /profile

现象：if (email !== undefined && EMAIL_RE.test(email)) u.email = email; 只校验格式，不查重、不做小写归一。而登录按 u.email.toLowerCase() === acc 匹配。

根因/影响：用户 A 可把邮箱改成用户 B 的邮箱（大小写不同也能绕过 B 的匹配），之后 B 用该邮箱登录会直接进入 A 的账号；改完密码则 B 彻底失去账号。

修复：改邮箱走验证码二次确认；统一 toLowerCase() 存储；查重（排除自己）；绑定邮箱仅通过 /bind-email 走验证码流程。

P2登录成功后的限流 key 清除写错（清不掉）server/routes/auth.js · POST /login（rateClear 调用）

现象：写入用 clientKey(req, 'pwd|' + acc)（含 IP），清除用 clientKey('pwd|' + acc)（IP 位恒为 'x'）——key 不匹配，成功登录后计数不会清零，同一 IP 连续输错仍会触发 60 秒锁。

修复：清除时同样传 req：rateClear(clientKey(req, 'pwd|' + acc))。

P2重置密码邮件匹配大小写敏感server/routes/auth.js · POST /send-reset-email

现象：查询用户用 u.email === email（未 toLowerCase），而注册/登录侧都做了归一。用户资料里若曾写入带大写字母的邮箱（见上一问题），重置时会"该邮箱未绑定账号"。

修复：统一 (u.email || '').toLowerCase() === email.toLowerCase()。

P1文件上传无内容嗅探，管理端允许 SVG 上传（存储型 XSS 向量）server/routes/user.js · POST /upload；server/routes/admin.js · /admin/upload

现象：上传仅按 ext 参数写文件，不校验文件头；管理端上传接受 svg，SVG 可内嵌 <script>/onload，之后以 <img src> 形式被前台/后台渲染。

根因/影响：上传的 SVG 在用户浏览器上下文执行脚本可窃取登录态、改写页面；属于存储型 XSS。

修复：用 magic bytes 嗅探真实类型并严格白名单（jpg/png/webp/gif）；禁止 svg 或对 svg 做消毒（移除 script/事件属性）；设置 CSP img-src 限制。

P2注销账号不清理关联数据，与管理员删用户口径不一致server/routes/user.js · DELETE /account

现象：注销只删用户本体（及会话），orders/aftersales/chat/tickets/messages 全部残留且不标 userDeleted；而管理端删用户会标 userDeleted。残留数据在后台仍展示为正常用户。

修复：统一走"软删除"：标 userDeleted=1 + 清敏感信息 + 保留订单快照；管理端列表过滤已注销用户。

P2售后申请可重复提交（仅拦截 pending）server/routes/user.js · POST /orders/:id/aftersale

现象：拦截条件 ['pending'].includes(a.status) 只挡"处理中"；一笔订单被驳回或同意后仍可再次提交，可反复骚扰/重复退款风险。

修复：同一订单仅允许一条售后记录（或允许"已驳回"后重新提交但去重处理中的记录，并在 UI 明确规则）。

订单与售后管理

P1退款恢复"幽灵卡密"：分站手动发货的卡密被错误回收server/routes/admin.js · refundOrder

现象：退款时把 c.orderId === o.id 的全部卡密置回 unused。但分站手动发货写入的卡密（productId 指向分站商品 id，不属总站卡池）也会被恢复为 unused。

根因/影响：分站商品走 manual stock，卡密是手工填写的"一次性内容"；恢复后既不会重新入库（分站商品不查卡池），又变成孤儿数据，且若再次发货同一订单会重复给卡。

修复：仅回收"总站卡池"的卡密（c.source === 'pool' 或 productId 属于总站商品）；分站手动卡密只做展示不回收；退款消息中说明卡密作废。

P1售后驳回对话框：点"取消"也会提交驳回public/js/admin.js · 售后管理 data-no 处理

现象：const reply = (await dialog({...})) ? '' : ''——三元两个分支都是空串，if (reply === null) return 永不成立。管理员点"再想想"取消后，请求照样发出并把售后驳回。

根因/影响：误操作直接驳回用户退款申请，引发客诉；属于前端交互逻辑 bug。

修复：先判返回值：const r = await dialog(...); if (!r) return; 驳回理由让用户在对话框内输入（dialog 支持输入时），而不是静默用默认文案。

P2订单改价只改 payAmount，goodsAmount/couponAmount 不变，对账口径断裂server/routes/admin.js · PUT /admin/orders/:id/price

现象：改价仅 o.payAmount = amount，商品金额与优惠不变。若用户有优惠券，实际抵扣与展示不一致；销售额统计用 payAmount，而商品行合计用 goodsAmount，两边对不上。

修复：记录 priceAdjust（调价差额），展示层统一按 payAmount 呈现，统计口径注明含调价；或同步调整 goodsAmount。

P2自动发卡取卡无随机/无锁，极端并发可能重复发同一张卡server/settle.js · 自动发货取卡

现象：发卡用 pool[i] 顺序取卡，无锁、无随机。Node 单线程下同步段内安全，但涉及异步（回调重入、并发下单）时仍有重复发放窗口；且长期顺序取卡会让最早批次卡密先耗尽。

修复：按商品原子取卡：crypto.randomInt 随机取 + 状态位 CAS；或为每个商品维护取卡游标并在事务中更新。

P2自动确认/自动取消依赖接口触发（无定时任务）server/routes/user.js · autoProcessOrders

现象：autoProcessOrders 只在支付/查询等接口被调用时顺带执行。长时间无人访问时，超时订单不取消、超期订单不自动确认。

修复：启动时挂 setInterval（如每 5 分钟）扫描执行；或引入 cron 任务。

P2资金写入依赖 150ms 防抖落盘，进程崩溃可能丢最近数据server/db.js · save / mutate；server/settle.js

现象：db.save 带 150ms 防抖 + 异步写文件；结算、扣款、分成等资金路径没有显式 flushNow()。进程在防抖窗口内崩溃（或写盘失败），最近的订单/资金变动丢失。

修复：资金与订单关键路径（settlePaidOrder / creditBranchShare / 提现审核 / 余额调整）在响应前调用 db.flushNow()；写盘失败时返回 500 而不是 200。

商品 / 分类 / 卡密模块

P2商品发货类型（auto↔manual）切换不处理库存/卡密server/routes/admin.js · PUT /admin/products/:id

现象：切换 type 时只改字段：auto→manual 后卡池卡密不再被使用，但库存没迁移；manual→auto 后原有 stock 直接归零（stock: type==='manual' ? ... : 0），若已售订单引用旧库存无影响，但管理员视角商品突然"无库存"。

修复：切换时明确提示并二选一：auto→manual 把剩余卡密数量写入 stock；manual→auto 把 stock 清零并提示"改为卡池发放"。保留切换审计。

P2优惠券金额/用户积分可设负数server/routes/admin.js · POST/PUT coupons、PUT users

现象：满减券 amount: Number(amount) || 0 无下限（可填 -100，下单反而加钱）；折扣券 PUT 时无 clamp（新建有 0.01-0.99）；用户积分 u.points = Number(points) 可负。

修复：金额/积分统一 Math.max(0, ...)；折扣统一 clamp 到 [0.01, 0.99]；前端输入加 min。

P2订单/购物车购买数量无硬上限（仅前端 999）public/js/app.js · vCheckout buy 模式；server calcOrder

现象：buy 模式数量直接来自 URL 参数，前端 stepper 上限 stock，但 URL 手改可绕过；后端仅 isFinite 校验、无数量上限与 stock 上限。

修复：后端统一 1 ≤ qty ≤ min(stock, 999)，非法直接报错。

P2验证码/订单号用 Math.random 生成（可预测）server/util.js · genCode / genOrderNo

现象：Math.random() 非加密随机。验证码可预测则短信/邮箱验证码爆破；订单号可预测则接口枚举（配合其他漏洞）风险上升。

修复：改用 crypto.randomInt()（验证码）与 crypto.randomBytes（订单号），并保证订单号唯一性检查。

P2个人中心订单角标用 size=100 全量拉取统计，订单多时不准public/js/app.js · vUser

P2管理端消息群发仅能选前 50 个用户public/js/admin.js · aMessages

修复：下拉改远程搜索/分页，或仅保留"全部/按等级"。

前端通用（体验 / 健壮性）

P2轮播/聊天轮询定时器不随路由清理，页面切换后残留空转public/js/app.js · vProduct / vService（swiperTimer / pollTimer）

现象：商品页轮播 setInterval 与客服页 3 秒轮询 pollTimer 是全局变量；切走页面后旧定时器继续跑（操作已销毁的 DOM 或持续请求接口），产生多余请求与潜在报错。管理端 chatPoll 已做清理，用户端没有。

修复：路由 render 前统一 clearInterval（与 admin 一致），或在视图卸载钩子里清理。

P2支付宝 iframe sandbox 缺 allow-top-navigation，returnUrl 跳转受限public/js/app.js · vPay 在线支付视图

现象：iframe sandbox="allow-forms allow-scripts allow-same-origin" 不允许顶层导航，支付宝支付完成后 returnUrl 无法自动跳回，只能靠 10 分钟轮询兜底。

修复：加 allow-top-navigation（或改 window.open 外链支付页）；同时注意 allow-scripts + allow-same-origin 同开的安全风险（避免引入第三方内容时组合使用）。

P2支付页轮询 10 分钟超时，与订单 30 分钟自动取消不一致public/js/app.js · vPay pollPay；settings.pendingCancelMinutes

现象：前端扫码倒计时固定 10 分钟，到点提示"支付超时"；但订单实际 30 分钟才自动取消（设置可改）。10 分钟后用户仍在 pending 状态，文案与事实不符。

修复：倒计时读取 settings.pendingCancelMinutes，或到点后提示"订单仍可继续支付"。

P2管理端登录页硬编码默认账号密码提示public/js/admin.js · aLoginView

现象：登录页写死"默认账号：admin　默认密码：admin123"。若管理员从未改密码，等于把钥匙贴在大门上；即使改过，也诱导攻击者定向爆破。

修复：删除提示；后端检测管理员仍是默认密码时返回警告并要求强制改密。

P2系统设置保存后整页刷新；wechatCertPath 被固定清空public/js/admin.js · aSettings

现象：保存设置后 location.reload()；且提交体固定 wechatCertPath: ''，若后端支持证书路径配置会被每次保存覆盖为空。

修复：改局部刷新；certPath 与内联证书二选一提交，不传即保留原值。
