二、缺陷修复明细

编号级别模块问题与根因修复方案验证结果
BUG-001P1 严重下单 / 库存 并发下单超卖。下单（pending）时不预留库存，库存=1 的商品可被连续/并发创建多个订单，支付环节才扣减，存在超卖与重复支付纠纷风险。 下单临界区加进程内串行锁（withOrderLock），并引入未付款订单库存占用校验：可售量 = 现有库存 − 待付款/待确认订单占用量，锁内重查最新数据后再建单；订单取消/超时自动释放占用。 已验证
库存=1 并发 6 单，仅 1 单成交，其余返回「库存不足」。
BUG-002P1 严重支付回调 回调收到误标 Content-Type: application/json 的表单串时，express.json() 在中间件层抛错，统一回 500，渠道判定通知失败会反复重试甚至关闭回调。 ① 全局错误中间件识别解析错误（entity.parse.failed）回 400；对 /api/pay/notify/* 一律按渠道规范应答纯文本 failure，不回 500。② 回调路由新增 parseNotifyParams()，基于 rawBody 兼容表单串/JSON 两种编码。 已验证
误标 JSON 表单回调 → 400 + failure；正常表单编码回调不再 500。
BUG-003
BUG-004		P2 一般直接购买 负数 / 0 / 超上限 / 非数字购买数量被 Math.max(1, parseInt(q)||1) 静默钳为 1，产生业务歧义和异常订单。 立即购买分支改为严格校验：数量必须是 1–999 的整数，否则返回「购买数量不合法」，不再静默修正；结算试算同步加固数量与占用校验。 已验证
-1 / -100 / 0 / 1000 / "abc" / null 全部被拒；1 与 999 正常。
BUG-005
BUG-006		P2 一般注册 / 个人资料 昵称存在存储型 XSS。注册与「修改资料」均未过滤 HTML/脚本，恶意昵称（如 <script>、<img onerror>）入库后在后台/前台渲染可执行。 注册与改资料昵称入库前统一经 util.sanitizeHtml() 剥离所有标签并 trim；纯标签/空值回退默认昵称，改资料在净化后再做 2–20 长度校验。 已验证
<script>alert(1)</script>小明<b>粗 存储为「小明粗」，无任何标签。
BUG-007P2 一般登录 / 会话 无登出接口，POST /api/auth/logout 返回 404，Token 在 7 天有效期内始终有效，前端仅清除本地存储，Token 泄露后无法主动失效。 后端新增 POST /api/auth/logout，按请求头 Token 精确删除服务端会话（用户/管理员/分站通用）；用户端、管理后台、分站后台三端「退出登录」均已接入该接口（keepalive 静默调用）。 已验证
登出后旧 Token 再访问受保护接口返回 401。
BUG-008P2 一般全局异常 全局 JSON 解析错误统一回 500 并回显 SyntaxError 内部信息，状态码语义错误且泄漏实现细节。 全局错误中间件按 err.status 区分 400/500；400 返回通用「请求格式错误」，500 返回「服务器内部错误」，均不回传异常原文，错误详情仅写服务端日志。 已验证
非法 JSON 返回 400「请求格式错误」，响应体不含任何内部信息。
FUND-01资金加固退款 / 售后 重复退款导致积分被重复扣回（测试中新发现）。订单先经「订单退款」退为已退款后，关联售后单仍为待处理，再点「同意退款」会二次执行退款逻辑，重复扣回积分、重复推送退款消息。 refundOrder() 增加幂等保护：订单已退款/已取消直接跳过并返回 false；售后「同意退款」前校验订单状态，仅待发货/待收货/已完成可退，已退款等状态明确拒绝，杜绝二次资产冲正。 已验证
已退款订单再走售后同意 → 被拦截；该订单积分「退款扣回」流水仅 1 条（修复前为 2 条）。
