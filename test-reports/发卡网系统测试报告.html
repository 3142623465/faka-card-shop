3. 缺陷清单（按严重度）

3.1 严重缺陷（H）— 2 项

H-1 商品价格可为负数，导致 0 元购 已复现
涉及：POST /api/admin/products · GET /api/shop/products · POST /api/user/orders

现象：管理员创建商品时传 price: -100，服务端 Number(price)||0 对负数不拦截（-100 为真值），商品成功入库显示「¥-100」；用户下单时 payAmount = Math.max(0, ...) 被钳制为 0 元，支付金额为 0 即可获得商品（复现：创建负价商品 → 下单 payAmount=0 → 模拟支付成功发货）。

影响：管理员误填/被诱导填写负价时，商品等于免费发放；若开放商品创建权限给分站，将成为套利通道。

修复建议：创建/更新商品时强制校验 price >= 0（建议 > 0 或价格下限 0.01）；下单时对 payAmount 为 0 的订单做二次校验或直接拒绝。
H-2 配置文件中明文存放 QQ 邮箱授权码 静态确认
涉及：server/config.js（email.auth.code: 'xfhdzreujddrdgif'）

现象：真实邮箱 SMTP 授权码明文硬编码于项目配置文件。虽然 .gitignore 已排除 config.js，但源码共享、备份、误传仓库、工单截图等场景均可能泄露。

影响：授权码可被用于冒用邮箱发送钓鱼邮件，泄露账号身份。

修复建议：改由环境变量（SMTP_AUTH_CODE）或密钥管理服务注入；config.js 只留占位符并加「必须通过环境变量配置」的启动校验。

3.2 中等缺陷（M）— 6 项

M-1 卡密去重为全局维度，跨商品误拦截 已复现
涉及：POST /api/admin/products/:id/cards（去重条件 d.cards.some(c=>c.code===e.code)）

现象：卡密 code 在全库唯一校验。若商品 A 已含「ABC123」，为商品 B 添加同格式「ABC123」会被提示「没有可添加的卡密（已存在）」，无法上架相同卡密格式的第二商品。实际业务中不同商品常共用同一批卡密模板。

修复建议：去重范围限定为 c.productId === 当前商品；如需全局唯一（防重复售卖），应在前端/文档明确提示并允许管理员选择去重范围。
M-2 管理后台缺少基础安全响应头（CSP / X-Frame-Options） 已复现
涉及：server.js（无安全头中间件）

现象：全站响应无 Content-Security-Policy、X-Frame-Options / frame-ancestors。虽前端 XSS 转义整体到位，但一旦出现未转义点即可被利用；且管理后台存在被「点击劫持」的风险面。

修复建议：增加 helmet 或手写中间件，至少配置 frame-ancestors 'none'、CSP（self + data: 图片）、X-Content-Type-Options: nosniff。
M-3 删除用户/上级分站不级联清理分站，遗留孤儿分站且无法删除 已复现
涉及：DELETE /api/admin/users/:id、DELETE /api/admin/branches/:id

现象：删除分站 owner 用户后，其分站仍保留在 branches 表（ownerId 指向已删用户）；管理后台再次删除该分站时提示「专业分站不存在」（因 requireBranchOwner 查不到 owner），形成永久死数据。测试中复现 10+ 个孤儿分站。

修复建议：删除用户时级联删除其名下分站及下级；或允许管理员删除无 owner 的孤儿分站；删除专业分站时递归处理下级。
M-4 密码哈希算法强度不足（SHA-256 加盐） + 卡密使用 Math.random() 生成
涉及：util.js hashPassword、genCardCode

现象：密码使用 SHA-256（单轮）加盐，未采用 bcrypt / scrypt / argon2 等慢哈希；卡密/订单号等随机串使用 Math.random()（非加密安全随机）。前者在数据库泄露时可被 GPU 高速爆破，后者卡密可被预测（结合时序可枚举）。

修复建议：密码改用 crypto.scrypt（内置，无依赖）或 bcryptjs；卡密生成改用 crypto.randomBytes 并编码。
M-5 支付回调在未配置平台证书时跳过验签（生产误配置风险）
涉及：payments.js handleWechatNotify / handleAlipayNotify

现象：未配置 WX_PLATFORM_CERT 或 ALI_PUBLIC_KEY 时，回调仅打印警告后直接按成功处理（不验签）。当前沙箱默认开启缓解了风险；但若生产部署忘记上传平台证书，攻击者可伪造回调免费发货。

修复建议：未配置证书时拒绝真实渠道回调（返回验签失败），仅允许模拟渠道；启动时对生产模式做配置完整性校验。
M-6 验证码 devCode 直显能力依赖环境判断，误配置即形同虚设
涉及：captcha.js / sms.js / email 相关（development 模式 API 返回 devCode）

现象：开发模式下短信/邮箱/图形验证码通过 API 直接回传（便于本地调试），仅靠 NODE_ENV 区分。若运维以 development 模式部署（常见于新手），任意人可调用 send-code 接口直接读取验证码完成注册/改密/找回密码。

修复建议：生产模式启动时强制校验 NODE_ENV=production 且阻断 devCode 返回；devCode 逻辑增加独立开关并默认关闭。

9.4 新发现严重缺陷

H-3 商家确认收款后订单不结算、不发货，卡死 pending_confirm 已复现
涉及：POST /api/admin/orders/:id/confirm-pay（admin.js:460-475）→ settle.settlePaidOrder（settle.js:66-70）· 手动支付主链路

现象：手动支付订单进入 pending_confirm 后，管理员调用确认收款接口，接口返回成功（{"msg":"已确认收款","status":"pending_confirm","autoShipped":false}），但订单状态保持 pending_confirm 不变：不结算、不发卡、不产生「支付已确认」消息。经代码定位：settlePaidOrder 的幂等保护 if (o.status !== 'pending') return {ok:true,...} 把 pending_confirm 误判为「已结算订单」直接短路返回；而 confirm-pay 传入的正是 pending_confirm 订单。git 历史确认该矛盾与「手动转账支付」功能同时引入，功能从未真正联调通过。

影响（严重）：① 手动转账支付核心链路彻底不可用——用户付款后商家无法确认，商品永不发货；② 订单可被无限次重复确认（每次返回成功但不改变状态），幂等性缺失；③ 因订单仍处 pending_confirm，用户仍可取消已收款订单，形成「商家收了钱、用户退款」的资金风险；④ 卡死订单既不能结算也不能删除（管理端删除接口仅允许 pending/cancelled/refunded），成为永久数据垃圾。

修复建议（二选一）：① 在 settlePaidOrder 幂等保护中加入 pending_confirm：if (o.status !== 'pending' && o.status !== 'pending_confirm')（推荐，恢复「确认收款=结算发货」语义）；② 在 confirm-pay 中先校验 pending_confirm，再调用结算。修复后需回归：确认收款 → 自动商品发货 + 卡密锁定 + 消息通知；重复确认被拒；已确认订单不可取消。对应自动化用例见 api-test-manual-pay.js 第 5/6/7 区块（修复后应全部转 PASS）。
