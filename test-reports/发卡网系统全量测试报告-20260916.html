四、缺陷详情（含根因定位与修复代码）

BUG-001 P1 高危 并发下单超卖 — 库存检查非原子操作，竞态条件导致库存为负
模块下单结算测试端后端 API
前置条件存在库存为 1 的手动发货商品（如商品 ID=37），用户已登录并添加收货地址
复现步骤使用 Promise.all 同时发送 5 个 POST /api/user/orders 请求，购买同一库存为 1 的商品
预期结果最多 1 个订单创建成功，其余返回"库存不足"
实际结果5 个订单全部创建成功（成功数=5），导致超卖
证据并发测试脚本输出：成功数=5；security-test-results.json 中 BUG-SEC-004

根因定位

server/routes/user.js:269-300，calcOrder() 函数与下单路由之间无锁/无事务。流程为：读库存 → 检查 → 扣减 → 保存，多请求并发时均通过库存检查后才各自扣减，导致竞态。本地 JSON 存储无原生事务支持。

修复建议

引入内存级互斥锁（单进程 Node.js 适用），将"检查+扣减+创建订单"放入临界区；或使用乐观锁（版本号/CAS）。以下为内存锁修复方案：

// server/routes/user.js — 在文件顶部添加
const orderLocks = new Map(); // productId -> Promise chain
function withProductLock(productIds, fn) {
  const key = [...productIds].sort().join(',');
  const prev = orderLocks.get(key) || Promise.resolve();
  const next = prev.then(fn, fn);
  orderLocks.set(key, next.catch(()=>{}).then(() => {
    if (orderLocks.get(key) === next) orderLocks.delete(key);
  }));
  return next;
}

// 下单路由内：将库存检查+扣减+订单创建包裹在锁内
router.post('/orders', auth.requireUser, (req, res) => {
  // ... 解析参数、地址校验 ...
  const pids = items.map(i => i.productId);
  withProductLock(pids, async () => {
    const d = db.load();
    const calc = calcOrder(d, items, coupon); // 内部检查并扣减库存
    if (calc.error) return res.json(util.fail(calc.error));
    // ... 创建订单、保存 ...
    db.save();
    res.json(util.ok({ orderId: order.id, ... }));
  }).catch(e => res.json(util.fail('下单失败，请重试')));
});

回归验证方法

修复后重新运行并发测试：5 个并发请求购买库存=1 商品，应仅 1 个成功；检查 db.json 中该商品 stock ≥ 0。

BUG-002 P1 高危 支付回调收到非 JSON body 时返回 500 — 全局错误处理中间件未区分解析错误状态码
模块支付回调测试端后端 API
前置条件服务运行中，存在待支付订单
复现步骤POST /api/pay/notify/alipay（或 /wechat、/xunhu），Header Content-Type: application/json，Body 为表单串 out_trade_no=xxx&order_no=xxx
预期结果回调入口优雅拒绝，返回渠道要求的 success/failure 纯文本，HTTP 400，不产生 500
实际结果HTTP 500，响应体 {"code":1,"msg":"服务器内部错误：Unexpected token 'o', \"out_trade_\"... is not valid JSON"}
证据backend-deep-test-results.json [05-支付与发货]；logs/error-20260916.log 第1/12/37/48行多次记录此 SyntaxError

根因定位

server/server.js:47 全局挂载 express.json()，对所有 Content-Type: application/json 的请求强制 JSON.parse。当支付渠道（或中间代理）误标 Content-Type 但 body 实为表单串时，中间件层抛出 SyntaxError（err.status=400）。server/server.js:84-88 的全局错误处理中间件未读取 err.status，统一返回 500 并暴露内部错误信息。

关联：server/routes/pay.js:66（alipay）、:101（xunhu）直接信任 req.body，未做 raw body 容错解析。

修复建议（两层修复）

第一层：全局错误处理区分状态码（server/server.js:84-88）

app.use((err, req, res, next) => {
  const status = err.status || err.statusCode || 500;
  console.error('[server] 异常(' + status + '):', err.message);
  try { require('./logger').error('http', err); } catch(e) {}
  res.status(status).json({
    code: 1,
    msg: status === 400 ? '请求格式错误' : '服务器内部错误'
  });
});

第二层：支付回调路由使用 raw body 并容错（server/routes/pay.js）

// 在 pay.js 顶部为回调路由单独注册 raw 解析
const expressRaw = express.raw({ type: '*/*', limit: '1mb' });

router.post('/notify/alipay', expressRaw, (req, res) => {
  let params = {};
  const raw = req.body.toString('utf8');
  try {
    // 兼容 JSON 和表单两种格式
    params = raw.startsWith('{') ? JSON.parse(raw) : Object.fromEntries(new URLSearchParams(raw));
  } catch (e) {
    console.warn('[pay] 支付宝回调body解析失败，返回failure:', e.message);
    return res.send('failure');
  }
  // ... 后续验签逻辑不变
});

回归验证方法

修复后分别发送：(1) 正确表单编码回调 → 验签失败返回 failure；(2) 误标 JSON 的表单串 → 返回 400 或 failure，不再 500；(3) 正确 JSON 微信回调 → 正常验签流程。

BUG-003 P2 中危 负数购买数量未被拒绝 — 静默钳制为 1 并成功下单（E12）
模块下单结算测试端后端 API
前置条件用户已登录，已添加收货地址，存在在售商品
复现步骤POST /api/user/orders Body: {"from":"buynow","productId":1,"quantity":-5,"addressId":xxx}
预期结果{"code":1,"msg":"购买数量不合法"}
实际结果{"code":0,"data":{"orderId":81,"payAmount":98,"orderNo":"20260916121945527757"}} — 订单创建成功，数量被静默钳为 1
证据backend-deep-test-results.json [04-下单结算] E12；api-test-edge.js E12；security-test-results.json BUG-SEC-001

根因定位

server/routes/user.js:315，buynow 分支：

items = [{ productId: Number(productId), quantity: Math.max(1, Math.min(999, parseInt(quantity) || 1)) }];

Math.max(1, ...) 将负数静默钳制为 1，导致 calcOrder()（user.js:277）中的 q < 1 校验永远触发不到。API 不告知客户端数量非法，存在业务逻辑歧义。

修复建议

// server/routes/user.js:314-315 替换为
if (from === 'buynow') {
  const rawQty = parseInt(quantity);
  if (!Number.isInteger(rawQty) || rawQty < 1 || rawQty > 999) {
    return res.json(util.fail('购买数量不合法（1-999）'));
  }
  items = [{ productId: Number(productId), quantity: rawQty }];
}

回归验证方法

修复后发送 quantity=-1、-100、0、1000、"abc"、null，均应返回 code=1；quantity=1、999 应正常下单。

BUG-004 P2 中危 数量 0 未被拒绝 — parseInt(0)||1 短路求值退化为 1（E13）
模块下单结算测试端后端 API
前置条件同 BUG-003
复现步骤POST /api/user/orders Body: {"from":"buynow","productId":1,"quantity":0,"addressId":xxx}

修复建议

与 BUG-003 共用同一修复代码（严格校验原始 quantity，避免 ||1 兜底 0）。

回归验证方法

修复后 quantity=0 应返回 code=1；quantity=1 正常下单。

nickname: util.sanitizeHtml(nickname) || '用户' + email.split('@')[0],

BUG-007 P2 中危 无注销/登出接口 — Token 无法主动失效，退出后仍可使用
模块认证-Token测试端后端 API
复现步骤用户登录获取 Token → 前端点击退出 → POST /api/auth/logout → 返回 404 接口不存在；使用原 Token 访问 GET /api/user/profile → 仍返回 200
预期应有 logout 接口，登出后当前 Token 立即失效
实际无 logout 路由，Token 在 7 天 TTL 内始终有效，前端仅清除本地存储
证据security-test-results.json BUG-SEC-007；POST /api/auth/logout 返回 404

根因定位

server/routes/auth.js 模块中未定义 logout 路由。系统使用服务端 session 存储（db.sessions），但缺少从 session 中删除当前 Token 的入口。

修复建议

// server/routes/auth.js — 添加
router.post('/logout', auth.requireUser, (req, res) => {
  const h = req.headers['authorization'] || '';
  const m = /^Bearer\s+(.+)$/i.exec(h);
  if (m) {
    const d = db.load();
    d.sessions = (d.sessions || []).filter(s => s.token !== m[1]);
    db.save();
  }
  res.json(util.ok({ msg: '已退出登录' }));
});

同时建议管理后台"禁用用户踢下线"功能已验证可清除该用户全部 session（PASS），普通用户登出只需清除当前 Token。

回归验证

登录获取 Token → 调用 logout → 用原 Token 访问需认证接口 → 应返回 401。

BUG-008 P2 中危 全局 JSON 解析错误统一返回 500 而非 400 — 暴露 Express 内部错误信息
模块全局健壮性测试端后端 API
复现步骤任意 Content-Type: application/json 的 POST 接口发送非法 JSON body，如 {"email":"test",broken
预期HTTP 400，返回 {"code":1,"msg":"请求格式错误"}
实际HTTP 500，返回 {"code":1,"msg":"服务器内部错误：Expected double-quoted property name..."}，暴露内部解析细节
证据security-test-results.json BUG-SEC-008

根因定位

server/server.js:84-88，全局错误处理中间件未读取 err.status。express.json() 解析失败时设置 err.status = 400，但中间件忽略此字段统一返回 500，并将 err.message（含 Express 内部解析细节）直接暴露给客户端。

修复建议

与 BUG-002 第一层修复相同，修改 server/server.js:84-88：

app.use((err, req, res, next) => {
  const status = err.status || err.statusCode || 500;
  console.error('[server] 异常(' + status + '):', err.message);
  res.status(status).json({
    code: 1,
    msg: status === 400 ? '请求格式错误' : '服务器内部错误'
  });
});

回归验证

向登录接口发送非法 JSON → 应返回 400 且 msg 不含内部解析细节；向不存在接口发送 → 404；正常请求 → 正常响应。

BUG-009 P1 高危 分站用户名超 20 字符截断后重复校验失效 — 可创建重复账号且无法登录
模块分站开通测试端后端 API
前置条件已存在一级分站，可通过邀请链接为用户开通下级分站；或管理员直接调用 POST /api/branch/branches
复现步骤使用超过 20 字符的 username（如 test_longname_1234567890_ab@test.com）连续两次调用 POST /api/branch/branches 开通分站
预期结果第二次应返回 {"code":1,"msg":"该分站账号已被使用"}
实际结果第二次成功创建重复分站（实测 id=21 与 id=22，username 均被截断为 test_longname_12345678）；且该分站用完整邮箱登录时按 username 查不到，返回"账号或密码错误"
证据branch-test-results.json 中 "POST /api/branch/branches / 超长用户名重复创建(截断校验)" 用例；long1=21, long2=22 均创建成功

根因定位

server/routes/branch.js:116 取 un 后，:125 查重使用原始 username（未截断），而 :131 落库使用 un.slice(0,20) 截断值。两次使用不同的值导致查重失效。同时 branch.js:37 登录时按 username 精确查找，截断后的账号无法用完整邮箱匹配。

修复建议

// server/routes/branch.js — 在取 un 后立即统一截断，查重与落库使用同一值
// 修改前（有漏洞）:
const un = String(username || '').trim();
// ... line 125 查重用 un（未截断）
// ... line 131 落库用 un.slice(0, 20)

// 修改后:
const un = String(username || '').trim().slice(0, 20);
// 后续查重与落库均使用 un（已统一截断）

同时建议：登录时对输入的 username 也做相同的 .slice(0,20) 归一化，确保截断账号可正常登录；或在注册/开通时拒绝超过 20 字符的用户名而非静默截断。

回归验证方法

修复后：(1) 用 >20 字符 username 连续开通两次 → 第二次应被"账号已被使用"拦截；(2) 用 20 字符以内 username 开通 → 正常创建；(3) 用截断后的 username 登录 → 应成功；(4) 已有正常分站登录不受影响。
